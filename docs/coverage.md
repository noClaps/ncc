# Specification coverage inventory

This is a static inventory of [the language specification](design.md), audited
against test sources on 2026-10-05 at baseline `3c8759c`. It maps requirements to
existing assertions, not implementation status. Passing tests do not establish
full conformance, absence of undefined behavior, or agreement on unspecified
semantics. The specification was not changed for this audit. The targeted syntax,
optional-tuple, scalar-operator, pattern, generic-error-payload, and async-void
coverage added after the baseline is recorded in the corresponding rows below.

Every specification section is represented below, including the builtin keyword
index and each row of the conversion table. Closely related requirements share
rows. References are representative entry points, not an exhaustive list of every
assertion. A listed test does not establish coverage of all combinations of types,
nesting, empty values, boundary values, failure paths, or compiler modes.

## Reading the evidence

- **P**: positive execution with NC assertions or exact expected output.
- **N**: rejected compilation with an asserted diagnostic.
- **R**: successful compilation followed by an asserted runtime failure.
- **F**: lexer/parser assertions, without generated-program execution.
- **C**: compilation, diagnostics, or generated-C assertions only.
- **O**: generated-C optimization assertions in addition to behavioral evidence.
- **D/R**: both NC debug and release modes, not the Cargo build profile.
- **D**: default/debug compilation or execution only.
- **Gap**: no dedicated assertion located in this audit. This is not proof that
  no such assertion exists, or that the compiler lacks the feature.

### Harness limits

- `conformance::{success,rejects,runtime_failure}` check both modes. Runtime
  failures must compile successfully, exit with code 1, and contain the expected
  diagnostic; they are not interchangeable with compile-rejection cases.
- `error_payloads::success` executes explicit test roots through `ncc test` in
  both modes and asserts successful exit and exact stdout.
- `optimizer::folded` compiles both modes and normally executes both, comparing
  exact output. Listed function names additionally check release removal.
  **Exception:** calls whose function-removal list contains the exact name
  `signed` skip debug execution; `fibonacci_uses_each_numeric_types_range` is
  release-executed only.
- Mixed conformance/optimizer fixtures containing tests wrap outside executable
  statements in synthetic test roots. Use actual CLI tests for evidence about
  dependency slicing, top-level scope, and imported test execution.
- `frontend::repaired_design_examples_parse_and_type_check` compiles illustrative
  programs in both modes but does not execute their branches or assert results.
- Branch syntax, an unused declaration, or an `assert false` fallback not reached
  by a fixture is not evidence of that branch's successful behavior.
- Unicode oracle unit tests are mode-independent frontend evidence. Generated C
  and execution tests are needed separately for debug/release behavior.
- `nc-tests/*.nc` are examples, not automatically asserted conformance tests.
  `strings.nc` is included by `output::original_strings_example_with_reduced_work_has_only_final_output`
  at 4,096 iterations, not its full workload. The Fibonacci optimizer fixture is
  inline, not execution of `nc-tests/fibonacci.nc`. `builtins.nc` must not be run
  with uncensored output because it prints environment variables.

   scalar truth/comparison tables, bitwise OR/XOR/complement, integer spellings
   and same-scope shadowing now have dedicated P D/R assertions. Safe integer
   arithmetic and exact binary-fraction float arithmetic now have operator samples;
   generic inclusion covers nominal/structural/optional elements. Signed
   quotient/remainder, negative powers and other unresolved numeric cases remain blocked.
3. **Patterns/control flow:** incomplete Boolean/struct/tuple coverage;
   fixed-array pattern length errors. Recursive discarded-tree payloads and
   boundary-distinct string subjects now have dedicated P D/R assertions.
4. **Errors/generics:** construction/return/throw restrictions for errors.
   Direct scalar optional throw fallback now has P D/R result, laziness and
   Unicode/NUL message assertions. Chained generic/nominal/container functions, structs and enums now
   have P D/R assertions for substituted fixed/dynamic/map/tuple/optional payloads
   and deep copies. Recursive generic array/map structs and enum branches now add
   P D/R traversal, rebuilding, all variants/empty containers and independent deep
   copies with constant/runtime inputs. Mutually recursive/imported types and

   bare `identity<Count>` is not currently parsed as a callable value.

   cross-feature combinations remain expandable. Never assert a particular racing outcome.
6. **Modules/externs:** selective/wildcard rejection; multi-import initialization
   and state identity after clarification; multi-file cycles; extern
   visibility/literal/scope/call restrictions; backend errors. Direct exported
   nominal aliases, repeated private-state mutation through one import and an

7. **Builtins/CLI:** invalid builtin matrix; embed missing/symlink/permission negatives

   and silent no-tests behavior now have P D/R source/artifact assertions. Process-state
   positives now check executable-name/empty/Unicode arguments, controlled absent

   Remaining process-state failure edges are not covered by those positives. Boolean casts now

## Semantics questions to resolve before new conformance expectations

This list records questions, not answers. Existing implementation behavior or
passing tests must not decide the intended semantics. Some may be answered by a
more precise reading or a user decision without a specification edit; any edit to
`design.md` requires explicit approval.

| Area                             | Question / specification tension                                                                                                                                                                                                                                                                                                           |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Indexed reads                    | When index evaluation mutates/replaces the object, which snapshot is read and validated? Known evaluator/C discrepancy is already tracked separately in TODO; keep folding/proof barriers until resolved. Assignment rules do not automatically define reads.                                                                              |
| Operator typing                  | The same-type rule exempts only pipe, while inclusion and differently sized fixed-array concatenation require compatible but different operand types. What is the general rule, and is the mentioned but undefined pipe operator intended language scope?                                                                                  |
| Numeric failures                 | Define signed quotient/remainder, negative integral powers, `0**0`, invalid shift counts and compile-time versus runtime failure expectations. IEEE nonfinite arithmetic/C extern values, their formatting and integer-conversion failures, negative float→uint, and signed right-shift rounding are already resolved, not open questions. |
| Indexing/destructuring           | Negative array indexing is already prohibited and optional tuples must be handled before destructuring. Clarify failure phase/diagnostics for invalid runtime indices, empty `$` and `$-n` underflow, and tuple constant-index requirements. Add explicit unwrap/destructuring tests without assuming implicit flow narrowing.             |
| Multiline/Unicode                | Define tabs, under-indented/blank lines, inline closing delimiters, initial/final newlines and CRLF. Identify the grapheme Unicode version and normalization contract; distinguish precomposed characters from decomposed scalar sequences. Existing boundary-preserving string operations are already resolved.                           |
| Representation                   | Are bool's one-byte storage and array's internal `cap/vals` normative observable ABI promises or illustrative internals? Cast/value tests alone do not establish layout.                                                                                                                                                                   |
| Maps                             | Define permitted key domain and NaN-key lookup expectations, duplicate literal keys, and failure for absent reads. Concatenation's right-hand overwrite and lack of stable traversal order are already resolved.                                                                                                                           |
| Function results / caught errors | Does consumption include arbitrary expression/return/condition contexts? Which storage/passing/casting operations are allowed on caught `error`, versus ordinary return/construction restrictions?                                                                                                                                         |
| Pattern exhaustiveness           | Define omitted struct fields and combined nested finite partitions across struct/tuple/enum/Boolean alternatives. Do not derive general rules from a few irrefutable patterns.                                                                                                                                                             |
| Lock jump targets                | Conditional text describes bare break targeting a loop, while mutex examples permit exiting a lock. What wins when lock/loop/value contexts compete? Existing individual lock exits do not settle all nested combinations.                                                                                                                 |
| Future lifecycle                 | Background start/caller continuation and mutex exclusion are already required. What exactly is discarded at scope exit: handle, detached work, or work after a join? How do unobserved worker failures affect termination, and what scheduling/fairness guarantees exist? Keep tests deterministic rather than timing-based.               |
| Permitted races                  | Which observable outcomes and storage/lifetime guarantees exist for ordinary raced scalars/containers? Nonfatal warnings and allowed nondeterminism do not by themselves eliminate generated-C undefined behavior.                                                                                                                         |
| Module identity                  | Are imports initialized once across aliases/transitive paths? Specify path normalization, shared private state and initialization order before asserting a module-instance contract.                                                                                                                                                       |
| Optimization scope               | The specification promises broad evaluatable folding/infinite-loop warnings; tests document conservative proof domains. Clarify the normative completeness expectation without claiming all termination is decidable or silently weakening the language.                                                                                   |
| External examples                | Etch examples remain in the specification, but project scope is C-only. Record this mismatch without implementing Etch or altering the specification. C ownership/lifetime and malformed foreign values need a separate ABI/UB audit.                                                                                                      |

## Maintenance and verification

When adding a regression, update its row with the actual asserted property and
modes. Keep compile-only, rejection, runtime failure, execution and optimization
assertions distinct. Remove a gap only after the relevant assertion exists; do
not mark an entire feature complete because one happy path passes.

After the positive generic/nominal/container, arithmetic/conversion/inclusion,
composite async error-union, direct optional throw, recursive generic, locked
async payload and successful CLI artifact/argument additions, repository verification passed:
`cargo test --offline`, `cargo test --offline --no-default-features`,
`cargo clippy --offline --all-targets -- -D warnings`, `cargo fmt --check`, and
`cargo build --offline --release`. Those results validate the current regression
suite, not all inventory requirements. The new fixtures assert specified positive
behavior with constant/runtime-dependent inputs in debug and release; no compiler
or specification changes were made. Successful execution/stdout assertions in
`positive_operators_conversions` permit nonfatal C compiler diagnostics.
